# [Chapter 6 補足] ハッシュタグ追加画面を作ろう

Chapter 6 では、入力したハッシュタグを API に送信し、詳細画面に表示しました。
ここでは、保存に失敗した時に再試行できるようにし、一覧画面にも追加したハッシュタグが表示されるようにしてみましょう。

ハッシュタグをレシピに紐付けるという、今回の講義用の仕様は同じです。

## 仕様

Chapter 6 の仕様に加えて、以下の動きを満たすようにしてみましょう。入力するテキストのトリム方法と、POST リクエストで送信する項目は元の章を参照してください。

### ハッシュタグの入力と保存

- トリムしたテキストが空の場合は、API リクエストを送らない
- 保存中は「ハッシュタグを追加する」ボタンと入力欄を無効にする
- 保存中はキャンセルボタンやスワイプ操作で画面を閉じられないようにする
- 保存に失敗したら、入力したテキストを残し、エラーメッセージを表示する
- 失敗した後は、再び保存ボタンを押してリクエストを送ることができる

### 保存に成功した時

- ハッシュタグ追加画面を閉じる
- 詳細画面と一覧画面の両方に、追加したハッシュタグが表示される

今回は、元の章にあった成功時のアラートは表示せず、画面を閉じた後のハッシュタグ表示で結果を確認することにします。

## 参考

### ViewModel に入力と保存の状態を保持する

元の章では ViewModel の作成は任意でしたが、完成サンプルでは`AddRecipeHashtagsViewModel`を作成しています。入力したテキストに加え、保存中かどうかとエラーメッセージを、この ViewModel に保持します。

[AddRecipeHashtagsViewModel.swift](../../MiniCookpad/View/AddRecipeHashtags/AddRecipeHashtagsViewModel.swift) を開くと、以下の property があります。

```swift
var text = ""
private(set) var isSaving = false
private(set) var errorMessage: String?
```

`isSaving`と`errorMessage`は、View から値を読めますが、変更できるのは ViewModel の中だけです。入力用の`text`は、TextField から変更できるようにしています。

View 側では ViewModel を`@State`で保持し、`body`の中で以下のように Binding を作ります。

```swift
@Bindable var model = viewModel
TextField("#タグ1 #タグ2（スペース区切り）", text: $model.text, axis: .vertical)
```

`$model.text`を渡すことで、入力したテキストが ViewModel の`text`に書き戻されます。`@State`と`@Bindable`の違いについては [Observation の補足](state.md) も見てみてください。

### 保存ボタンを押した時の処理

保存する処理は、ViewModel の`save()`メソッドに記述します。このメソッドは非同期なので、ボタンから呼び出す時は`Task`で囲います。

```swift
Task {
    if await viewModel.save() {
        dismiss()
    }
}
```

`save()`は保存に成功すると`true`を返します。その場合だけ`dismiss()`を呼ぶことで、失敗した時は入力画面にとどまることができます。

では、保存中にもう一度ボタンが押されることを防ぐには、どうすればよいでしょうか。

View では`disabled`という Modifier を使ってボタンを無効にします。加えて、ViewModel 側でも送信してよいかを確認します。完成サンプルの`save()`は、以下の処理から始まります。

```swift
guard canSave else { return false }
isSaving = true
errorMessage = nil
defer { isSaving = false }
```

`canSave`は、保存中ではなく、トリムしたテキストが空でもない場合に`true`になる計算プロパティです。これをメソッドの先頭で確認することで、ボタン以外から呼び出された場合にも、送信してよいか判断できます。

`isSaving`は、API リクエストを`await`する前に`true`にします。処理が終わったら、成功したかどうかにかかわらず`false`に戻したいので、`defer`を使っています。

### 保存に失敗した時の表示

保存に失敗した場合は、`text`を変更せず、`errorMessage`にメッセージを設定します。View では、この値がある場合にメッセージを表示してみましょう。

完成サンプルは`Form`と`Section`を使って画面を作っています。メッセージが増えたり、キーボードが表示されたりしても、スクロールして操作できるようにするためです。

[AddRecipeHashtagsView.swift](../../MiniCookpad/View/AddRecipeHashtags/AddRecipeHashtagsView.swift) の実装も参考にしてみてください。

### 一覧と詳細にハッシュタグを表示する

POST リクエストのレスポンスには、今回追加したハッシュタグが入っています。既存のハッシュタグをこのレスポンスで全て置き換えると、以前から付いていたものが消えてしまいます。

そのため、[RecipeStore.swift](../../MiniCookpad/Library/RecipeStore.swift) では、既存の配列に新しいハッシュタグを追加しています。同じ ID のものがあれば、その要素を置き換えます。

一覧と詳細は同じ Store のハッシュタグを表示しているので、ここで値を変更すると、Observation によって両方の表示が更新されます。詳細画面に戻る時の`onAppear`や、一覧に戻る時の再取得で更新しているわけではありません。

ここまでできたら、シミュレータで`＃夕食　＃簡単`と入力して保存してみましょう。詳細画面に追加したハッシュタグが表示されたら、一覧に戻って表示を確認してください。もう一度詳細を開いたり再読み込みしたりしても、同じハッシュタグが表示されていれば OK です。

失敗した時の動きも、エラーを返す API クライアントに差し替えて確認してみてください。入力したテキストが残っていて、再試行できることを確認しましょう。

## [補足 1] 保存中に画面を閉じる操作

今回は、ユーザーが始めた保存は結果が返るまで待つことにします。保存中はキャンセルボタンを無効にし、`interactiveDismissDisabled`でシートをスワイプして閉じる操作も無効にしています。

ボタンの中で作った`Task`は、View が消えると自動でキャンセルされるものではありません。そのため、別の理由で画面が消えても、成功した結果を Store に反映できます。ただし、アプリを終了した後も処理を続ける仕組みではありません。

また、通信が失敗したように見えても、サーバー側では既に保存が完了している場合があります。実際のサービスで再試行を扱う時は、同じ要求を受け取っても重複して保存しない仕組みを、サーバー側と合わせて考える必要があります。

## [補足 2] 取得と保存の順序が入れ替わる場合

最後に、通信が重なった場合について少し補足します。以下の順序で処理が進んだらどうなるでしょうか。

1. ハッシュタグの取得を始める
2. 取得が終わる前に、新しいハッシュタグの保存が成功する
3. 最初に始めた取得が終わり、新しいハッシュタグを含まない結果が返ってくる

最後の結果で Store を上書きすると、保存したばかりのハッシュタグが消えてしまいます。

完成サンプルでは、レシピ ID ごとに更新回数を保持しています。保存に成功したら回数を増やし、取得開始時の回数と比べることで、その間に保存が行われたかを確認します。保存が行われていれば、取得結果でハッシュタグを上書きしません。

`@MainActor`を付けていても、`await`で待っている間には別の操作が実行されるので、この確認は必要です。今回は同じ Store の中で起きる取得と保存の重なりを扱い、他の端末との同期までは扱いません。

[Chapter 7](../chapter_07.md) では、この順序をテストで再現してみます。
