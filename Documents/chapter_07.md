# テストでアプリの動作を確認しよう

前の章までで、ハッシュタグを追加し、一覧と詳細に表示できるようになりました。
この章では、通信に失敗した場合や、複数の通信が重なった場合にも正しく動くことを、テストで確認してみましょう。

- Swift Testing を使って ViewModel や Store の動作を確認する方法
- 非同期処理の順序をテストで制御する方法
- UI テストを使って画面を操作する方法

について学んでいきます。

今回は、完成サンプルに既に追加されているテストを実行し、その実装を読んでいきます。

## テストを実行する

まず、Xcode で実行先に iOS シミュレータを選択してください。
メニューの「Product」から「Test」を選ぶか、`⌘U`を押すとテストを実行できます。

テストには、結果を指定できるテスト用 API クライアントとサンプル API を使っています。外部サーバーを起動する必要はありません。

テストが完了したら、結果を確認してみましょう。失敗したものがあれば、どのテストのどの行で失敗したかを Xcode で確認できます。

## ViewModel の動作をテストする

### Swift Testing

値の変換や ViewModel の動作を確認するテストには、Swift Testing を使います。
`import Testing`で利用でき、テストする関数には`@Test`を付けます。

[MiniCookpadTests.swift](../MiniCookpadTests/MiniCookpadTests.swift) を開いて、`emptyListDoesNotRequestTags()`を見てみましょう。以下は、その一部を抜粋したものです。

```swift
@Test func emptyListDoesNotRequestTags() async {
    let client = TestClient()
    client.recipes = []
    let model = RecipeListViewModel(store: RecipeStore(client: client))
    await model.request()
    #expect(client.tagRequests == 0)
    #expect(model.hasLoaded && model.items.isEmpty)
}
```

このテストでは、レシピが 0 件の場合に、ハッシュタグを取得するリクエストを送らないことを確認しています。順番に見ていきましょう。

### API クライアントを準備する

最初に、テスト用の API クライアントを作り、返すレシピを空の配列にしています。

```swift
let client = TestClient()
client.recipes = []
```

`TestClient`は、このテストファイルの中に定義したクラスです。実際の通信を行う代わりに、あらかじめ設定したデータを返します。

次に、このクライアントを使う Store と ViewModel を作成します。

```swift
let model = RecipeListViewModel(store: RecipeStore(client: client))
await model.request()
```

`request()`は、画面を表示する時にも呼んでいるメソッドです。テストの中から同じメソッドを呼び、処理が終わるまで待っています。

### 結果を確認する

最後に、`#expect`で結果を確認します。

```swift
#expect(client.tagRequests == 0)
#expect(model.hasLoaded && model.items.isEmpty)
```

`#expect`には、成り立ってほしい条件を書きます。条件が`false`になった場合は、そのテストが失敗します。

最初の行では、ハッシュタグの取得が一度も呼ばれていないことを確認しています。次の行では、レシピの取得が完了し、表示する項目が空であることを確認しています。単に配列が空かどうかだけでなく、「まだ取得していない」と「取得した結果が 0 件だった」を区別しているということです。

このように、結果を準備し、処理を実行し、期待する値と比べることで、View を表示しなくても ViewModel の動作を確認できます。

## 非同期処理をテストする

Chapter 6 の補足では、ハッシュタグの保存後に古い取得結果が返ってくる場合を考えました。この順序をテストで再現するには、どうすればよいでしょうか。

「0.5 秒待てば、まだ通信中のはず」といった待ち方では、端末の速さによって結果が変わってしまいます。そこで今回は、応答を一時停止するための`Gate`というクラスをテスト用に用意しています。

`staleGetCannotOverwriteSuccessfulPost()`の、以下の部分を見てみましょう。

```swift
let load = Task { try await store.loadRecipes() }
await gate.waitUntilEntered()
try await store.addHashtags(recipeID: 1, value: "#新規")
gate.release()
_ = try await load.value
```

最初にハッシュタグの取得を始め、`waitUntilEntered()`で応答を止める位置に到達するまで待ちます。その間にハッシュタグを保存し、`release()`で取得の応答を再開します。

これにより、以下の順序を再現できます。

1. 取得を始める
2. 応答を止めている間に、保存を完了する
3. 保存前のデータを含む取得結果を返す

その後の`#expect`で、保存したハッシュタグが残っていることを確認しています。待ち時間を予想する代わりに、処理を進める位置をテスト側から決めることができました。

## 他のテストも読んでみる

同じファイルには、以下のような場合のテストも用意しています。

- 全角のハッシュタグやスペースを含む入力をトリムする
- 空の入力では POST リクエストを送らない
- リクエストの JSON に、正しいキーと値が入っている
- ハッシュタグの返却順が変わっても、レシピ ID で組み合わせられる
- 取得に失敗した後、再試行できる
- キャンセル後に返ってきた取得結果でデータを更新しない
- ハッシュタグの保存に成功すると、一覧と詳細の両方が更新される
- 同じ ID のハッシュタグが重複しない
- 保存中にもう一度`save()`を呼んでも、二重に送信しない
- 保存に失敗した場合は、入力したテキストが残る
- サンプル API に追加したハッシュタグが、次の取得でも返ってくる

まず一つ選んで、どのような結果を準備し、何を確認しているかを読んでみましょう。

## UI テスト

ここまでは、ViewModel や Store のメソッドを直接呼んで確認していました。では、ボタンを押した時に保存処理が呼ばれることや、入力した値が渡されることは、どう確認すればよいでしょうか。

アプリを起動し、画面を操作するテストには、XCTest と XCUIAutomation を使います。[MiniCookpadUITests.swift](../MiniCookpadUITests/MiniCookpadUITests.swift) を開いてみましょう。

このテストでは、以下の操作を行います。

1. 一覧から詳細画面を開く
2. ハッシュタグ追加画面を開いて、テキストを入力する
3. 保存ボタンを押す
4. 詳細画面にハッシュタグが表示されることを確認する
5. 一覧へ戻り、同じハッシュタグが表示されることを確認する

ViewModel のテストが通っていても、View とつながっていなければ、ユーザーは操作できません。UI テストでは、実際の操作の流れを通して確認しています。

入力する文字の細かな違いなどは Swift Testing で確認し、UI テストでは画面をまたぐ一連の操作を確認する、という使い分けにしています。

## 課題

ここまで読めたら、以下を試してみましょう。

- テスト用 API が返すハッシュタグの順番を変えても、一覧のテストが通ることを確認する
- Store の更新回数を比べる処理を一時的に外し、保存後に古い取得結果が返るテストが失敗することを確認する（確認できたら元に戻してください）

余裕がある方は、通信を待っている間に詳細画面を閉じる UI テストも追加してみてください。

## [補足] テストごとにインスタンスを作る理由

各テストでは、そのテスト用の API クライアントと Store を作っています。なぜ全てのテストで同じインスタンスを使わないのでしょうか。

Swift Testing は、複数のテストを並行して実行できます。インスタンスを共有していると、あるテストで書き換えた値を、別のテストが読んでしまうかもしれません。テストごとに作成することで、他のテストが変更したデータの影響を受けずに確認できます。

詳しく知りたい方は、[Apple のテストガイド](https://developer.apple.com/documentation/xcode/testing) も見てみてください。
