# テストで保存と画面の更新を確かめる

タグを追加し、一覧と詳細に表示されるところまで作れました。次は、通信に失敗した場合や、二つの通信が重なった場合にも正しく動くかをテストします。

値の変換や保存処理はSwift Testingで確認し、アプリの画面を実際に操作するテストにはXCTestとXCUIAutomationを使います。

## テストを実行する

Xcodeで実行先にiOSシミュレーターを選び、Product → Test（⌘U）を実行してください。テスト用の通信クライアントとサンプルAPIを使うため、外部サーバーを用意する必要はありません。

## 一つのテストを読んでみる

Swift Testingでは、テストする関数に `@Test` を付けます。期待どおりの結果になったかは `#expect` で確認します。

次は「レシピが0件なら、タグを取得する通信は不要」という動きを確認するテストです。

```swift
@Test func emptyListDoesNotRequestTags() async {
    let client = TestClient()
    client.recipes = []
    let model = RecipeListViewModel(store: RecipeStore(client: client))
    await model.request()
    #expect(client.tagRequests == 0)
    #expect(model.hasLoaded && model.items.isEmpty)
}
```

`TestClient` は、[テストファイル](../MiniCookpadTests/MiniCookpadTests.swift) に定義した通信クライアントです。ここでは空のレシピ一覧を返すように準備してから、通常の画面と同じ `request()` を呼んでいます。

最初の `#expect` で、タグの取得が一度も呼ばれていないことを確認します。次の `#expect` は、取得が完了し、表示する項目が空であることの確認です。「まだ取得していない」と「取得したが0件だった」を区別しています。

各テストでは、そのテスト専用のクライアントとStoreを作ります。複数のテストが並行して動いても、ほかのテストが変更したデータに影響されないようにするためです。

## 通信が重なる場面を再現する

保存と取得が重なるテストで「0.5秒待てば通信中のはず」と考えると、実行する端末の速さによって結果が変わってしまいます。

そこで、テスト用クライアントには応答を一時停止する `Gate` を用意しています。テストから停止位置への到達を確認し、必要な操作をしてから応答を再開できます。次のコードは、取得結果が返る前に保存を完了させる部分の抜粋です。

```swift
let load = Task { try await store.loadRecipes() }
await gate.waitUntilEntered()
try await store.addHashtags(recipeID: 1, value: "#新規")
gate.release()
_ = try await load.value
```

取得を始めた後、`waitUntilEntered()` で応答が止まったことを待ちます。その間にタグを保存し、`release()` で取得の応答を再開します。この順序を作ることで、古い取得結果が後から返ってきても、保存したタグが消えないことを確認できます。

## 完成サンプルで確認すること

テストは、次のような失敗しやすい場面を中心に用意しています。

| 対象 | 確認する動き |
| --- | --- |
| タグの入力と送信 | 全角の記号や空白を揃える。空入力を送らず、正しいJSONを作る。 |
| 一覧の取得 | タグの返却順が違っても、レシピIDで正しく組み合わせる。レシピが0件ならタグを取得しない。 |
| 失敗とキャンセル | 失敗後に再試行できる。キャンセル後の取得結果でデータを更新しない。 |
| 保存後の表示 | 再取得しなくても一覧と詳細にタグが反映され、同じIDのタグが重複しない。 |
| 保存中の操作 | 二重送信を防ぎ、失敗したら入力を残す。 |
| 通信の順序 | 保存後に古い取得結果が返っても、新しいタグが消えない。 |
| サンプルAPI | 追加したタグが、次の取得結果にも含まれる。 |

## 画面を操作するテスト

[UIテスト](../MiniCookpadUITests/MiniCookpadUITests.swift) ではアプリを起動し、一覧から詳細へ進み、タグを入力して保存します。その後、詳細にタグが表示され、一覧へ戻っても表示されることを確認します。

モデルのテストだけでは、ボタンが保存処理につながっているか、入力内容が正しく渡るかまではわかりません。UIテストでは、この一連の操作を通して確かめます。入力の細かなパターンはSwift Testingで確認し、UIテストでは画面をまたぐ代表的な操作を扱います。

## 確かめてみよう

1. テスト用APIが返すタグの順番を変えても、一覧のテストが通ることを確認しましょう。
2. Storeの更新回数を比べる処理を一時的に外して、古い取得結果が保存後に返るテストが失敗することを確かめましょう。確認したら元に戻してください。
3. 発展課題として、通信待ちの間に詳細画面を閉じるUIテストを追加してみましょう。
